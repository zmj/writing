One Year

November 24, 2026

One year ago today, Claude Opus 4.5 was released. A year ago, I would have described my occupation as “computer programmer”: I wrote code that created value for a business, and got paid handsomely for it. Today, in the same role, I write no code at all. What is my job, really?

Opus 4.5 was a watershed moment for AI coding. Before its release, I’d found AI coding narrowly useful: it could fill in a function body where the parameters and name made the behavior obvious, or write test cases following an established pattern. More ambitious tasks went off the rails as often as they succeeded, and weren’t worth the attempt compared to doing it correctly the first time.

Last December, the task in front of me was a proof-of-concept for a new microservice my team would build starting January (an email relay). My goal was to validate the tech stack and chosen libraries, demonstrating the end-to-end flow as a reference for the real implementation. Based on prior experience doing equivalent proof-of-concepts in unfamiliar domains, I’d allocated 2-3 weeks.

Using Opus 4.5, I was done in three days. I structured and sequenced the work as I normally would; the scope I’d plan for a productive morning was completed in a 15 minute Claude Code session. The code wasn’t exactly what I would have written, but it was within the bounds of what I’d planned, and would have approved if I were reviewing a teammate’s work. This was clearly how my job would be done going forward.

2026 has had a lot of doom and gloom about programming as a profession. The core, hard skill - writing code that reliably works as intended - has been automated. But I’ve picked up other useful skills around it: translating a desired product behavior into a series of code changes, figuring out how the code gets from my computer to servers executing it on the internet, and ensuring that it still works it in that environment. Those skills are harder to automate. They aren’t pass/fail; they’re choosing one solution from many workable options, optimizing against context-specific tradeoffs.

Context is the key word there. There’s nothing fundamental about those decisions that resists automation. Claude can’t make them as well as I can because it doesn’t have my context: the years of meetings with project stakeholders, understanding what solutions they’ll favor or resist; the history of the code, its infrastructure, and the bugs and incidents as it’s evolved; the understanding of the customer base, and where they’ll recognize value. That context has accreted in my head over time. It’s not written down for an agent to consume.

As a context engineering task, that’s not impossible to fix. “Everything gets written down” is the easy part. “Everyone can read everything” is harder, for cultural reasons. Radical transparency is rare in the corporate world. An even larger obstacle is individual incentives - once the context exists to automate substantial parts of a company’s decision-making layer, which roles are safe? Managers won’t reorg their own jobs out of existence, regardless of the company’s best interests. That kind of change can only be forced by external pressure.

To wrap up, I don’t think software engineering will disappear as a role at established companies. But that has more to do with corporate inertia than AI capabilities: the kind of company that doesn’t need software engineers also doesn’t need a lot of other decision-making functions. Companies can’t choose that transformation, because the people making the choice see their own heads on the chopping block. It will take external competition, and a clear verdict from the market - which for now, still works at human timescales.
